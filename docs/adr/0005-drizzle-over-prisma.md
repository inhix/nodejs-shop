# 0005. Drizzle ORM over Prisma

- Status: Accepted
- Date: 2026-11-25

## Context

The API needs typed database access that does not hide Postgres. Checkout locks rows
(`FOR UPDATE`), search uses full-text and trigram queries, products have JSONB attributes,
and admin reports group and join. Schema changes must go through committed migrations.
Drizzle is added with the first table in Phase 1; this ADR records the choice made in the
project brief.

## Decision

Drizzle ORM with drizzle-kit for migrations, on the `pg` driver.

- The schema is TypeScript; query result types come from it, with no code generation step.
- Migrations are generated by drizzle-kit, committed, never edited after merge, and run as
  a separate deploy step, never on app startup. drizzle-kit's `push` command (apply the
  schema directly, without a migration file) is not used.
- drizzle-zod derives Zod schemas from tables where it helps; API contracts stay in
  `packages/contracts`.

## Consequences

- Locking, full-text, JSONB and reporting queries stay typed instead of falling back to raw
  SQL.
- Queries map one-to-one to SQL, so performance is predictable and `EXPLAIN` output is easy
  to relate to code.
- Fewer conveniences than Prisma: no nested writes, a younger migration tool. Relations and
  transactions are written more explicitly.
- Drizzle is pre-1.0 and changes faster than Prisma; upgrades need attention.

## Alternatives considered

- **Prisma:** easier to learn, polished migrations and nested writes. Rejected because row
  locking, advanced search and reporting queries would need raw SQL, losing types where
  correctness matters most.
- **Kysely:** an excellent typed query builder, but no schema definition or migration
  generation; those would be ours to build.
- **TypeORM / MikroORM:** decorator-based entities fit Nest, but are heavier abstractions
  with less predictable SQL and weaker type inference for queries.
